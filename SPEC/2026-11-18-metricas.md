# Spec: Métricas de uso

- **Data:** 2026-11-18
- **Componente:** metricas
- **Status:** aprovada para implementação
- **Substitui:** nenhuma (detalha a linha 1 da tabela de `SPEC/2026-11-17-visao-geral-ap2.md`)

## O quê

O Filme Certo passa a registrar **eventos simples de uso** das funcionalidades novas da AP2 e do trailer, e a contar, **sem vincular a ninguém**, quais climas são escolhidos no wizard. Uma página `/metricas`, visível só para a dupla e os clientes, mostra os totais.

Esta spec entrega a infraestrutura (tabelas, funções, registro no servidor e no navegador, página de totais) e o primeiro evento em uso, `trailer_aberto`. Os eventos do wizard e do "Como foi?" passam a ser emitidos pelas specs dessas funcionalidades, usando o que esta spec define.

## Por quê

[Pedido do cliente, seção 3.1](../docs/ap2/pedido-do-cliente.md#31-métricas-de-uso-fazer-primeiro): "a AP2 pede evidência de uso, e nós também queremos saber se o wizard é usado e se as pessoas chegam até o fim. Sem medir, ninguém consegue responder." O pedido fixa três regras, e cada decisão abaixo serve a uma delas:

1. sem dados pessoais além do `usuario_id`;
2. as respostas de humor do wizard nunca ficam junto ao usuário;
3. uma consulta SQL ou uma página só para a dupla com os totais.

## Decisões técnicas

| Tema | Decisão |
|---|---|
| Lista de eventos | Fechada, no banco (`check`) e no código (zod). Ver a tabela "Eventos". Evento fora da lista é recusado |
| Dados de cada evento | `dados jsonb` com um schema zod por evento, só com valores de listas fechadas ou números pequenos. Nada de texto livre, título, e-mail ou nome |
| Climas fora dos eventos | O `check` de `eventos.dados` recusa as chaves `humor`, `experiencia` e `companhia`. Os climas só entram em `contagem_climas`, que não tem `usuario_id` |
| Granularidade dos climas | Um contador por **dia** e **por pergunta** (`humor`, `experiencia`, `companhia` separados). Sem horário e sem combinação das três respostas, para não dar para cruzar com o `wizard_concluido` de uma pessoa |
| Quem lê | Ninguém lê `eventos` nem `contagem_climas` diretamente (RLS sem `select`). Os totais saem de funções `security definer` que só respondem a quem está em `equipe_metricas` |
| Quem está na equipe | `equipe_metricas` é preenchida à mão no editor SQL do Supabase com os IDs da dupla e dos clientes. A tabela não tem políticas, então nenhum cliente da API a lê ou altera |
| Registro no servidor | `registrarEvento(supabase, evento)` valida, insere e **nunca lança erro**: devolve `true` ou `false` e só escreve no log. Métrica nunca quebra a tela |
| Registro no navegador | `enviarEvento(evento)` manda `POST /api/eventos` com `navigator.sendBeacon` (sobrevive ao `pagehide`, para o `wizard_abandonado`) e cai para `fetch(..., { keepalive: true })` sem ele. Corpo em `text/plain`, para o `sendBeacon` não precisar de preflight |
| Rota `/api/eventos` | Lê a sessão pelo cookie (`createClient` do servidor), valida com o mesmo schema e chama `registrarEvento`. `204` gravado, `400` inválido, `401` sem sessão. O cookie do Supabase é `SameSite=Lax`, então outro site não consegue postar em nome da pessoa |
| Contagem de climas | Função `registrar_clima(humor, experiencia, companhia)` (`security definer`), chamada no servidor por `registrarClima(supabase, respostas)`, também sem lançar erro |
| `trailer_aberto` | O componente `Trailer` ganha a prop opcional `origem`. Com ela, o clique em "Assistir trailer" chama `enviarEvento`. Sem ela, nada é registrado. Mudança localizada, coberta por teste |
| Página `/metricas` | Server Component na área logada. Chama as duas funções de totais; se o banco recusar (`42501`), responde `notFound()`, para quem não é da equipe nem saber que a página existe. Sem link no menu |
| Contas de teste | A coluna "sem a equipe" dos eventos exclui quem está em `equipe_metricas`. É ela que vale como evidência de uso real. Os climas, por serem anônimos, não têm essa separação |

### Eventos

| Evento | Quando | `dados` | Emitido por |
|---|---|---|---|
| `wizard_iniciado` | Abriu o wizard | `{}` | spec do wizard |
| `wizard_concluido` | Chegou à primeira recomendação | `{}` | spec do wizard |
| `wizard_troca` | Clicou "Esse não" e escolheu o motivo | `{ motivo: "ja-vi" \| "nao-e-o-clima" \| "muito-longo" \| "outro" }` | spec do wizard |
| `wizard_escolheu` | Clicou "Vou ver esse!" | `{ trocas: 0..5 }` | spec do wizard |
| `wizard_abandonado` | Saiu da página (`pagehide`) sem escolher | `{ etapa: "perguntas" \| "resultado" }` | spec do wizard |
| `como_foi_exibido` | A pergunta "Como foi?" apareceu | `{}` | spec do "Como foi?" |
| `como_foi_respondido` | Respondeu a pergunta | `{ resposta: "amei" \| "gostei" \| "nao-gostei" \| "nao-vi" }` | spec do "Como foi?" |
| `trailer_aberto` | Clicou em "Assistir trailer" | `{ origem: "filme" \| "noite" }` | **esta spec** (`origem: "filme"`); a spec do wizard usa `"noite"` |

Os valores de `motivo`, `resposta` e `origem` vêm do pedido do cliente (seções 3.2 e 3.3). Se o wizard precisar de outro valor, a spec dele ajusta esta tabela e o schema zod no mesmo commit.

### Climas

| Pergunta | Valores (slugs gravados) |
|---|---|
| `humor` | `cansado`, `animado`, `pra-baixo`, `nostalgico`, `ansioso`, `de-boa` |
| `experiencia` | `rir`, `emocionar`, `susto`, `tenso`, `pensar`, `distrair` |
| `companhia` | `sozinho`, `a-dois`, `familia`, `amigos` |

São as opções do pedido do cliente (seção 3.2). A spec do wizard usa os mesmos slugs.

## Banco de dados

Migration `supabase/migrations/20261118120000_metricas.sql`. Nenhuma tabela existente muda.

- **Tabela `public.eventos`**
  - `id bigint generated always as identity primary key`
  - `usuario_id uuid not null default auth.uid() references auth.users(id) on delete cascade`
  - `nome text not null check (nome in (...os 8 eventos...))`
  - `dados jsonb not null default '{}'`, com `check (jsonb_typeof(dados) = 'object')`, `check (not dados ?| array['humor','experiencia','companhia'])` e `check (pg_column_size(dados) <= 1024)`
  - `criado_em timestamptz not null default now()`
  - índice em `(nome, criado_em)` para os totais
  - **RLS:** uma política, `insert` para `authenticated` com `usuario_id = (select auth.uid())`. Sem `select`, `update` nem `delete`.
- **Tabela `public.contagem_climas`**
  - `dia date not null`, `pergunta text not null check (pergunta in ('humor','experiencia','companhia'))`, `resposta text not null`, `total int not null default 0 check (total >= 0)`
  - `check` que amarra `resposta` aos valores da tabela "Climas" de cada `pergunta`
  - `primary key (dia, pergunta, resposta)`
  - **RLS ligada e sem políticas.** Só a função abaixo escreve.
- **Tabela `public.equipe_metricas`**
  - `usuario_id uuid primary key references auth.users(id) on delete cascade`
  - **RLS ligada e sem políticas.**
- **Função `public.registrar_clima(p_humor text, p_experiencia text, p_companhia text) returns void`**
  - `security definer`, `set search_path = ''`. Exige `auth.uid()` não nulo (só quem está logado conta). Faz `insert ... on conflict (dia, pergunta, resposta) do update set total = total + 1` nas 3 linhas do dia (`(now() at time zone 'America/Sao_Paulo')::date`). Valor inválido falha no `check` da tabela.
  - `execute` só para `authenticated`.
- **Funções `public.metricas_eventos()` e `public.metricas_climas()`**
  - `security definer`, `set search_path = ''`, `stable`. Se `auth.uid()` não estiver em `equipe_metricas`, lançam `insufficient_privilege` (`42501`).
  - `metricas_eventos()` devolve `(nome text, total bigint, pessoas bigint, sem_equipe bigint)`, um por evento registrado.
  - `metricas_climas()` devolve `(pergunta text, resposta text, total bigint)`, somando todos os dias.
  - `execute` só para `authenticated`.

### Consulta SQL equivalente

Para rodar direto no editor SQL do Supabase (que ignora a RLS), como evidência:

```sql
select e.nome,
       count(*) as total,
       count(distinct e.usuario_id) as pessoas,
       count(*) filter (where e.usuario_id not in (select usuario_id from public.equipe_metricas)) as sem_equipe
from public.eventos e
group by e.nome
order by e.nome;

select pergunta, resposta, sum(total) as total
from public.contagem_climas
group by pergunta, resposta
order by pergunta, total desc;
```

### Como entrar na equipe

```sql
insert into public.equipe_metricas (usuario_id)
select id from auth.users where email in ('<email da dupla e dos clientes>');
```

## Código

```
src/features/metricas/
  eventos.ts          lista de eventos e schema zod (discriminado por nome); climas e seus slugs
  registrar.ts        registrarEvento(supabase, evento) e registrarClima(supabase, respostas)  (server-only)
  enviar.ts           enviarEvento(evento) no navegador (sendBeacon, ou fetch com keepalive)
  consultas.ts        obterMetricas(supabase): totais ou null se não for da equipe  (server-only)
  components/
    tabela-metricas.tsx   tabelas de eventos e de climas
src/app/api/eventos/route.ts     POST: sessão + schema + registrarEvento
src/app/(app)/metricas/page.tsx  página só da equipe
```

- `/metricas` entra em `ROTAS_PROTEGIDAS` do `proxy.ts`.
- `src/lib/supabase/database.types.ts` ganha as 3 tabelas e as 3 funções, editado à mão no formato gerado.
- A página do filme passa `origem="filme"` ao `Trailer`.

## Critérios de aceitação

1. `pnpm db:reset` aplica as migrations do zero sem erros (CI).
2. **Unitários** (`tests/unit/features/metricas/`, `tests/unit/app/`):
   1. o schema aceita cada evento com os dados da tabela e recusa evento desconhecido, `motivo`/`resposta`/`origem` fora da lista, chave extra (`humor`) e `trocas` acima de 5;
   2. `registrarEvento` insere `{ nome, dados }` no cliente injetado, devolve `false` sem lançar quando o banco falha ou o evento é inválido (e aí nem chama o banco);
   3. `registrarClima` chama `registrar_clima` com as três respostas e devolve `false` sem lançar em caso de erro ou resposta fora da lista;
   4. `enviarEvento` usa `sendBeacon` com o JSON do evento e, sem ele, `fetch` com `keepalive`; nunca lança;
   5. `POST /api/eventos` devolve `401` sem sessão, `400` para corpo inválido e `204` gravando o evento;
   6. `Trailer` com `origem` registra `trailer_aberto` com essa origem ao clicar; sem `origem`, não registra;
   7. `obterMetricas` devolve `null` quando o banco responde `42501` e os totais quando responde; a tabela mostra nome, total, pessoas e "sem a equipe", e os climas agrupados por pergunta com os rótulos em português.
3. **Integração** (`tests/integration/metricas/`, Supabase local):
   1. o usuário insere o próprio evento e não consegue ler nenhum evento, nem os próprios;
   2. o usuário não insere evento com o `usuario_id` de outra pessoa (`42501`);
   3. o banco recusa nome fora da lista e `dados` com a chave `humor` (`23514`);
   4. `registrar_clima` incrementa as três contagens do dia, e o usuário não lê `contagem_climas` nem `equipe_metricas`;
   5. `metricas_eventos()` e `metricas_climas()` lançam `42501` para quem não está na equipe. (Inserir alguém na equipe exige a chave de serviço, que os testes não usam; esse caminho é coberto pelo unitário 2.7 e verificado à mão na produção.)
4. `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` e `pnpm check:secrets` sem erros, e o CI verde.
5. Na produção, depois do merge e do `supabase db push`: abrir um trailer gera uma linha em `eventos`, e `/metricas` mostra os totais para quem está em `equipe_metricas` e 404 para os demais.

## Fora do escopo

| Item | Onde fica |
|---|---|
| Emitir os eventos do wizard e do "Como foi?" | specs `wizard-noite` e `como-foi` |
| Gráficos, filtros por período, exportação | não planejado: a tabela de totais basta como evidência |
| Eventos das telas antigas (busca, listas, reações) | não pedido pelo cliente |
| Ferramenta externa de analytics (Vercel Analytics, PostHog) | não planejado: os dados ficam no Supabase da dupla, sob as regras acima |
| Expirar eventos antigos | depois, se o volume crescer |
